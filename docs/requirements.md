# DeskMate 要件定義書

版: 1.0 / 最終更新: 2026-07-26 / 対象: MVP（ハッカソン期間内実装）

本書は DeskMate の「何を作るか」を定義する。
「どう作るか」は [architecture.md](architecture.md)、状態の定義値は [status-definition.md](status-definition.md)、
プライバシー要件の詳細は [privacy-design.md](privacy-design.md) を参照する。

---

## 1. プロジェクトの目的

モニタ上部に設置したイベントカメラで机上の動きを取得し、ユーザの現在の状態を推定して、
PC 画面上の小さなキャラクターとして表現する。

目的は次の 3 点である。

1. **自分の作業状態の可視化**: 集中していた時間、休んでいた時間を、後から記録を漁らずに把握できる。
2. **周囲への状態共有**: 「今話しかけてよいか」の目安を、本人が説明しなくても伝えられる。
3. **プライバシーを保った状態取得**: 机上には書類・スマートフォン・PC 画面・私物といった個人情報が並ぶ。
   RGB 画像を一切使わず、輝度変化のみを取得するイベントカメラを用いることで、
   「何をしているか（内容）」ではなく「どのくらい動いているか（活動）」だけを扱う。

DeskMate が外部に出すのは、抽象化された状態名・継続時間・話しかけやすさの目安のみである。
イベントの生データ、点群画像、机上の位置情報は共有画面に一切出さない。

## 2. 解決する課題

| # | 課題 | DeskMate での解決 |
|---|------|------------------|
| C1 | 同室・同ラボの相手に話しかけてよいタイミングが分からず、集中を中断させてしまう | 抽象状態と「話しかけやすそう」の目安を共有画面に表示する |
| C2 | 自分がどれだけ集中していたか / 休んでいたかを把握できない | 状態と継続時間を常駐ウィジェットに常時表示し、履歴を詳細画面に表示する |
| C3 | 在席・作業状況の共有に Web カメラを使うと、机上の書類や画面内容まで写り込む | イベントカメラのみを使用し、RGB 画像を取得しない |
| C4 | イベントカメラを使っても、生データをそのまま共有すれば動きの形状が推測されうる | 生データは PC 内に留め、共有するのは抽象状態のみ。保存は既定で無効 |
| C5 | 状態表示が頻繁に切り替わると、見ている側が信用しなくなる | 平滑化（多数決・最小継続時間・ヒステリシス）を必須要件とする |
| C6 | イベントカメラでは「離席」と「着席して静止」を区別できない | 「離席中」と断定せず、観測事実の表現（例:「一定時間、動きを検出していません」）に限定する |

### 明示的な非目標

- 誰が机の前にいるかを識別すること（個人識別は行わない）。
- 何の作業をしているか（アプリ名・書類の内容・入力文字列）を推定すること。
- 生産性のスコアリングや評価。DeskMate は評価指標を出さない。
- 高精度な行動認識。MVP はルールベースであり、推定は「傾向」に留まる。

## 3. 想定ユーザ

### U1: 本人（プライマリ）

- 大学の研究室・オフィスで、1 日数時間デスクワークをする人。
- Windows PC を使用。モニタ上部にイベントカメラを設置できる。
- 自分の作業リズムを把握したい / 集中中に話しかけられて困った経験がある。
- 技術的知識は不要。設定は設定ファイルまたは初期設定画面から行う。

### U2: 周囲の人（セカンダリ）

- 本人と同じ部屋にいる同僚・研究室メンバー。
- 共有画面（サブモニタ、または本人の画面の隅）を横目で見る。
- DeskMate の内部動作は知らない。「今声をかけてよいか」だけを知りたい。

### U3: 開発者 / デモ実施者（MVP 期間中の主要ユーザ）

- ハッカソンの審査員に対してデモを行う実装者。
- 実カメラなしでも全機能を動かせる必要がある（ダミー入力）。
- 推定の過程（点群 → 特徴量 → 状態）を説明できる必要がある（詳細画面）。

## 4. ユースケース

### UC-1: 常駐して状態を表示する（U1）

1. ユーザが DeskMate を起動する。
2. 常駐ウィジェットが画面右下に最前面で表示される。
3. ウィジェットにキャラクター・現在の抽象状態・継続時間が表示される。
4. 状態が変わったときだけ、キャラクターが短いアニメーションで遷移する。

**事前条件**: イベント入力ソースが利用可能（MVP ではダミー入力）。
**事後条件**: 1 秒に 1 回以上、継続時間表示が更新される。

### UC-2: 推定過程を確認する（U1 / U3）

1. ウィジェットの「詳細」ボタンを押す。
2. 詳細画面が開き、点群 → 時間窓 → 動きの範囲 → 重心 → 変化量 → 領域別活動量 → 特徴量 → 状態 → 履歴が並んで表示される。
3. 画面上部に「RGB 映像を使用していません / 生データを外部送信していません」の常時表示がある。
4. 閉じると、点群配信は停止する（詳細画面が開いている間だけ配信される）。

### UC-3: 周囲に状態を共有する（U2）

1. ユーザが共有画面を開き、サブモニタ等に表示する。
2. 共有画面にはキャラクター・抽象状態・継続時間・話しかけやすさの目安・最終更新時刻のみが表示される。
3. 周囲の人はそれを見て、声をかけるかどうかを判断する。

**制約**: 共有画面には点群・特徴量・生データ・机上の位置情報を一切表示しない。

### UC-4: 推定と共有を止める（U1）

1. ユーザがウィジェットの「推定停止」を押す。
2. 入力の取り込みと推定が停止し、状態表示が「推定を停止しています」に変わる。
3. 共有画面も同じ表示になり、直前の状態は残らない。
4. 「共有停止」を押した場合は、推定は続くが共有画面はプライバシーモード表示のみになる。

### UC-5: デモを行う（U3）

1. デモモードで起動する。
2. ダミー入力がシナリオを自動で切り替え、状態が順に遷移していく。
3. 詳細画面で推定過程を、共有画面で最終出力を、同時に見せられる。
4. デバッグモードでは、状態を手動で切り替えて特定の表示を確認できる。

### UC-6: 録画データで再現する（U3）

1. 設定で入力ソースをファイル / HDF5 に切り替える。
2. 記録済みイベント列を再生し、同じパイプラインで推定を行う。
3. 再生速度を変更できる。

## 5. 機能要件

ID は実装・テストの参照キーとして用いる。

### 入力（FR-IN）

| ID | 要件 | 優先度 |
|----|------|--------|
| FR-IN-1 | イベント入力は `EventSource` インターフェースで抽象化し、推定処理と UI が通信方式に依存しないこと | 必須 |
| FR-IN-2 | ダミーデータ生成ソースを提供すること | 必須 |
| FR-IN-3 | ファイル（JSONL / NPZ）読み込みソースを提供すること | 必須 |
| FR-IN-4 | HDF5 録画データ読み込みソースを提供すること。ただし Metavision の HDF5 は ECF コーデック圧縮のため、WSL2 側で `.npz` へ変換する経路を正とする（[architecture.md](architecture.md) §7.3） | 任意（MVP 後） |
| FR-IN-5 | WebSocket / TCP / UDP / HTTP ソースを、既存コードを変更せずに追加できる構成であること | 必須（構成のみ） |
| FR-IN-6 | 1 イベントは `x`(int), `y`(int), `t`(int, µs), `p`(0/1) を持つこと | 必須 |
| FR-IN-7 | イベントは一定時間分をまとめたバッチとしてパイプラインに渡されること | 必須 |
| FR-IN-8 | 入力が途切れた場合に、停止せず「入力が途切れています」状態へ遷移すること | 必須 |

### 処理（FR-PR）

| ID | 要件 | 優先度 |
|----|------|--------|
| FR-PR-1 | イベント列を 100 ms〜1000 ms の時間窓に分割すること（既定 200 ms） | 必須 |
| FR-PR-2 | [status-definition.md](status-definition.md) に定義した全特徴量を各窓で算出すること | 必須 |
| FR-PR-3 | 机上を領域に分割し、領域ごとの特徴量を算出すること | 必須 |
| FR-PR-4 | 領域定義を設定ファイルから変更できること | 必須 |
| FR-PR-5 | 状態推定はルールベースで行い、後から学習モデルへ差し替えられること | 必須 |
| FR-PR-6 | 推定は単一窓ではなく、過去数秒〜数十秒の履歴を用いること | 必須 |
| FR-PR-7 | 平滑化（多数決・最小継続時間・ヒステリシス）を行い、短時間の頻繁な切替を抑止すること | 必須 |
| FR-PR-8 | 各状態の継続時間を秒単位で管理すること | 必須 |
| FR-PR-9 | 推定結果に信頼度（0.0–1.0）を付与すること | 必須 |
| FR-PR-10 | Voxel Grid 変換・時間ビン差分・差分 Voxel 重心 / 変化量を、拡張特徴量として算出できること（既定は無効） | 任意 |
| FR-PR-11 | パイプラインは実時間 1 秒あたり 1 秒未満で処理を終えること（後述の性能要件） | 必須 |

### 出力・UI（FR-UI）

| ID | 要件 | 優先度 |
|----|------|--------|
| FR-UI-1 | 常駐ウィジェット・詳細画面・共有画面の 3 画面を提供すること | 必須 |
| FR-UI-2 | 常駐ウィジェットは最前面表示・移動・最小化ができること | 必須 |
| FR-UI-3 | 状態が変化したときだけキャラクターに遷移アニメーションを行うこと | 必須 |
| FR-UI-4 | キャラクターは素材がなくても図形・絵文字・テキストで代替表示できること | 必須 |
| FR-UI-5 | キャラクター表示は後から画像 / GIF / スプライト / Live2D へ差し替えられること | 必須（構成のみ） |
| FR-UI-6 | 詳細画面に推定過程 10 項目（[demo-scenario.md](demo-scenario.md) §2）を表示すること | 必須 |
| FR-UI-7 | 共有画面には抽象状態・継続時間・話しかけやすさ・最終更新時刻のみを表示すること | 必須 |
| FR-UI-8 | 「話しかけやすそう」は直接観測値ではなく、複数状態から導出する二次指標として実装すること | 必須 |
| FR-UI-9 | 信頼度が閾値未満のとき、断定的な表示を避けること | 必須 |
| FR-UI-10 | UI 更新は 1 秒あたり 5 回以上（継続時間表示は 1 秒粒度）行うこと | 必須 |

### プライバシー（FR-PV）

[privacy-design.md](privacy-design.md) に詳細を定義する。要件 ID は PV-1〜PV-12 として同文書で管理する。

### 動作確認（FR-TE）

| ID | 要件 | 優先度 |
|----|------|--------|
| FR-TE-1 | 実カメラなしで全画面・全状態を確認できること | 必須 |
| FR-TE-2 | ダミー入力で 8 シナリオ（[demo-scenario.md](demo-scenario.md) §1）を再現できること | 必須 |
| FR-TE-3 | シナリオが時間経過で自動遷移するデモモードを提供すること | 必須 |
| FR-TE-4 | 状態を手動で固定できるデバッグモードを提供すること | 必須 |
| FR-TE-5 | 特徴量計算・状態推定・平滑化に単体テストがあること | 必須 |

## 6. 非機能要件

| ID | 分類 | 要件 |
|----|------|------|
| NFR-1 | 性能 | 1 窓（200 ms）あたりの特徴量抽出＋推定を 30 ms 以内に完了する（100,000 events/窓時） |
| NFR-2 | 性能 | 常駐ウィジェットの CPU 使用率が、平常時に 1 コア換算 10% 未満 |
| NFR-3 | 性能 | 詳細画面の点群描画は 10 fps 以上、描画点数は最大 5,000 点に間引く |
| NFR-4 | 応答性 | UI スレッドをブロックしない。推定処理はワーカースレッドで実行する |
| NFR-5 | 堅牢性 | 入力ソースの例外でアプリが終了しない。状態を `no_signal` にして再接続を試みる |
| NFR-6 | 移植性 | Windows 11 で動作すること。macOS / Linux は考慮するが検証対象外 |
| NFR-7 | 保守性 | 入力・特徴量・推定・UI が疎結合であり、それぞれ単体でテストできること |
| NFR-8 | 可搬性 | Python 仮想環境 + `pip install -r requirements.txt` のみで起動できること |
| NFR-9 | 国際化 | 表示文字列は日本語を既定とし、ラベル定義を 1 箇所に集約すること |

## 7. 対象範囲

### 今回の対象（PC 側・イベント受信後）

1. イベントデータ入力（インターフェース + ダミー / ファイル）
2. 時間窓分割
3. 特徴量抽出（全体 + 領域別）
4. 状態推定（ルールベース）
5. 状態の平滑化
6. 継続時間の計算
7. キャラクター状態への変換
8. デモ・詳細画面への表示
9. 共有画面への表示
10. ダミー / 録画データによる動作確認

### 対象外

- Raspberry Pi 側のプログラム
- イベントカメラのデバイス制御
- Raspberry Pi と PC 間の通信実装
- 実イベントカメラからのリアルタイム受信
- Discord / Slack など外部サービス連携
- クラウドへのデータ保存
- 深層学習モデルの開発

## 8. 前提と制約

| # | 前提 / 制約 |
|---|------------|
| A0 | 使用機材は **Raspberry Pi 5 + Prophesee GenX320**（参照リポジトリ `EVENT_CAMERA` で確認済み。[architecture.md](architecture.md) §24） |
| A1 | イベントデータは既に PC 側へ届いているものとする。通信方式は未決定 |
| A1b | DeskMate 本体は Windows ネイティブで動き、**Metavision SDK / OpenEB に依存しない**。SDK は Linux 専用のため（[architecture.md](architecture.md) §7.3 の制約 C-1・C-2） |
| A2 | イベントの座標系はセンサ座標（左上原点、x 右方向、y 下方向）。解像度は設定で与える。**既定 320×320（Prophesee GenX320）** |
| A3 | イベント時刻 `t` はセンサ基準の単調増加マイクロ秒。PC の壁時計とは同期していない |
| A4 | カメラはモニタ上部から机上を俯瞰する固定設置。設置後にカメラは動かさない |
| A5 | 領域（キーボード付近など）はユーザが設定ファイルで矩形指定する。自動キャリブレーションは行わない |
| A6 | 想定ユーザは 1 名。複数人の机は対象外 |
| A7 | イベントカメラだけでは「離席」と「着席して静止」を区別できない。断定表示は禁止 |
| A8 | 照明変化・モニタのちらつき・人の通過はノイズとして混入しうる |

## 11. 用語

| 用語 | 定義 |
|------|------|
| イベント | 画素の輝度変化 1 件。`(x, y, t, p)` |
| 極性 (p) | 輝度増加=1、輝度減少=0 |
| バッチ (EventBatch) | 入力ソースが一度に返すイベント列 |
| 時間窓 (Window) | 特徴量算出の単位。既定 200 ms |
| 領域 (Region) | 机上を分割した矩形。キーボード付近 / マウス付近 / 中央 / 左 / 右 / その他 |
| 抽象状態 (DeskStatus) | DeskMate が推定する 7 種の状態。[status-definition.md](status-definition.md) |
| 候補状態 (StatusEstimate) | 平滑化前の、1 窓ごとの推定結果 |
| 確定状態 (StatusSnapshot) | 平滑化後に UI へ渡す結果 |
| 話しかけやすさ (Approachability) | 確定状態と履歴から導出する二次指標。3 段階 |
| 活動量 (eps) | 1 秒あたりのイベント数 (events per second) |
